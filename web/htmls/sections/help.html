Help & Documentation

Guide

Learn how to use OA CLI via the Web interface and the Command Line.

🌐 Web Interface Usage

  • Explorers and tabs: Use Data Explorer ($content), Specs Explorer ($specs), and Assets Explorer (workspace assets/). Opening an item reuses the current tab; pin a tab to keep it open, use + for a new tab, or open the tab-list menu to find items when the bar is crowded. The toolbar keeps the selected path on the left and actions on the right.
  • Assets: Browse the workspace's assets/ directory. SVG, PNG, JPEG, WebP, and ICO files render in an image preview, with an option to open the served asset in a new tab.
  • File Comparison: Open a mapped JSON file to compare local and remote content side by side, navigate changes, ignore whitespace, and apply remote lines or hunks locally. Pull replaces the full local file; push publishes the full local file.
  • Specs: Edit a spec in the syntax-highlighted JSON editor, save it, and run Test from the toolbar. The Last run panel shows formatted validation results for that spec. Spec folders summarize passing, failed, and not-started specs and can run the folder tests.
  • Folder Comparison: Folder index.json metadata maps a service and collection; nested folders inherit that mapping and add path query values. Folder contents show local and remote presence.
  • Metadata and Git: Click files to view remote metadata, schemas, and Git status. Git status remains separate from remote comparison status.
  • Terminal Sidebar: The right sidebar allows you to execute commands directly. Clicking "Edit" or "Pull/Push" in the UI will pre-fill the terminal for you.
  • Live Config: Manage your settings.json directly in the Config section with support for encrypted values.
  • Workspace Sync: The status bar at the bottom shows your current Git branch and pending changes across the workspace.

💻 CLI Usage

  • oa pull [path]: Fetch data from remote services to your local workspace.
  • oa push [path]: Send local modifications back to the remote service.
  • oa monit <folder>: Poll a required folder for local and remote JSON changes. Safe remote-only changes are pulled; schema-valid local-only changes are queued and pushed as whole files. Conflicts are saved in file metadata and linked to the web conflict list. New local files always require explicit approval with --approve <file>.
  • oa test [path]: Run JSON-based test specifications with full request/response validation.
  • oa init: Bootstrap a new project structure, initialize Git, and provision remote application settings.
  • oa validate [path]: Verify JSON files against their schemas (Draft 2020-12) using .oa/schemas/<service>.<collection>.schema.json and supporting $ref.
  • oa config [key] [value]: View or update CLI settings (e.g., oa config logger.level debug).
  • oa remote [file] [url]: Map a local file to a remote resource URL for easy syncing.
  • oa serve: Start this interactive web documentation server locally.
  • Monitor cadence is configured in minutes with oa config monit.pullIntervalMinutes 5 and oa config monit.pushIntervalMinutes 5. Both default to five minutes. Run oa serve to open conflict links in the web UI.

Monitor behavior: The first scan runs immediately. If a file has no saved baseline, the monitor pulls the complete remote file and saves it as the baseline. Remote-only changes also pull the full JSON file; local-only changes are schema-validated and queued for full-file push; divergent edits after a baseline exists create unresolved metadata conflicts. New files are held for explicit approval and are never auto-pushed. Click Monitor Logs in the activity toolbar to search logs by date, file, operation, error type, or message. Daily JSON-lines logs are flat files directly under .logs, with path components joined by __. The monitor checks for local edits before writes and never locks a file. Missing endpoint schemas block pushes. The remote transport currently has no conditional-write support, so a remote update can still race the final check.

Approve one new file:

oa monit data/system/applications --approve data/system/applications/test.json

Project Lifecycle:

oa init

Validation:

oa validate ./data/system/applications/console.json

Pro tip: Use --help with any command for detailed options.

⚙️ Key Concepts

Project Bootstrap

oa init sets up your directory structure, secret keys, and Git state. It also offers to provision your application on the remote server interactively.

Endpoint Schema Resolution

Schema validation resolves the endpoint from file metadata or the data/<service>/<collection> path and loads the corresponding schema from .oa/schemas/.

$prefixes

Use $content, $specs, and $oa to refer to standard workspace locations (like .data and .oa) reliably.
